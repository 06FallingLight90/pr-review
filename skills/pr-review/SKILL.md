# 通用 PR/MR 审查（Universal PR Review）

一套不依赖具体项目的 PR 审查方法论。核心立场：**审查不仅要找出 bug，更要回答四个问题**——①改动是否与项目既有结构、理念、契约一致；②改动是否符合项目的贡献原则（CONTRIBUTING）；③PR 声称的功能是否真的实现到位；④实现中隐藏了哪些问题。

①②④由**一致性轴**子代理承担，③由**实现度轴**子代理承担；两轴以**并行子代理**隔离执行（见第 2 步），主 agent 负责备输入、派发、聚合，并负责修复、测试、文档、合并的后续闭环。

## 何时使用

- 用户要求审查 PR / MR / commit / 分支差异，给出链接、编号或 diff。
- 用户要求评估改动与文档/协议/项目结构是否一致。
- 用户要求合并前做最终检查、或对合并提出疑问。
- 用户对 PR 提出结构性判断题（文件放置、是否应入仓、方案取舍）。

## 第 0 步：拉取改动

- 检出 PR 分支到工作区（或确认本地已有），保证可直接审查 diff。
- 检出前记录当前分支与工作区状态（`git branch --show-current`、`git status`），供收尾还原。
- 记录：基准分支、改动文件清单、提交信息、PR 声称的目标。

## 第 1 步：理解意图与范围

- 明确 PR「声称做什么」：读描述、标题、commit message。
- 按类别分组改动文件：新增/修改/删除 × 源码/测试/文档/配置/工程文件。
- 找出「超出声明范围的夹带改动」，判断是否合理。

## 第 2 步：并行两轴审查

审查主体是**两个并行子代理**（一致性轴 / 实现度轴），隔离执行防止一轴掩盖另一轴。主 agent 负责备齐输入、派发、聚合。

### 2.1 备齐轴输入（主 agent）

- diff 范围：基准分支、改动文件清单（第 0/1 步产出）、提交信息清单（`git log --oneline`）。
- 标准来源：探测贡献指南文件（`CONTRIBUTING`、`CONTRIBUTING.md`、`CONTRIBUTING.rst`、`CONTRIBUTE.md` 等，含大小写变体）、协议/API 规范/接口契约文档（唯一事实来源）、README、协作说明（如 CLAUDE.md）；记录文件路径与关键内容。
- spec 来源：PR 描述、标题、commit message 中的「声称做什么」（第 1 步产出）。完全找不到任何声称时，跳过实现度轴，并在最终报告注明「无 spec 可对照」。

### 2.2 派发

用 Agent 工具在**同一条消息里并行派发**两个 general-purpose 子代理。两个 prompt 都必须自带：diff 命令与提交清单、对应来源文件的内容——**子代理没有主会话的上下文，规范与清单必须全文粘贴进 prompt**。两轴汇报各限 400 字。

### 一致性轴子代理 prompt 要点

- diff 命令与提交清单。
- 标准来源文件清单与内容（契约文档、CONTRIBUTING、README 结构约定等）。
- 排查清单（下方 10 项）**全文粘贴**——子代理没有其他途径拿到它。
- brief：「逐项报告：(a) diff 违反项目明文契约/规范/贡献原则的每一处：引用出处（文件 + 规则原文）；(b) 目录结构越权、重复、遗留或未按 README/既有约定放置；(c) 违背项目核心理念与约定处（fail-closed vs fail-open、同步/异步、串行/并发、错误处理策略、资源管理约定、生成物 vs 手写代码边界）；(d) 行为/接口变化未同步 CHANGELOG、README（目录结构）、协作说明、专门对齐文档处；(e) mock/stub 与真实实现并存时行为不一致、测试无法驱动多个目标处；(f) 按排查清单逐项过出的问题：每项含位置、级别（[阻塞]/[应修]/[建议]）、原因、修复建议。区分硬违规与 judgement call：明文约定可硬判，项目明文约定压过通用判断，清单项一律是 judgement call；跳过工具已强制的检查。贡献指南缺失时注明，依据仓库历史与既有约定判断一致性，不强行套用外部规范。不超过 400 字。」

排查清单（粘进 prompt 的原文）：

1. **构建/配置**：多配置矩阵（Debug/Release × Win/x64、不同工具链）是否齐全一致；依赖/包含路径是否有遗漏或写死。
2. **资源管理**：内存/句柄/连接/文件泄漏；失败路径是否释放；回调/异步线程是否持有悬垂指针（应持 `shared_ptr` 等所有权语义）。
3. **清理顺序**：销毁/关闭顺序是否符合框架/中间件规范（先子后父、先实体后容器）。
4. **状态一致性**：操作失败时容器/缓存/状态是否仍更新或仍被查询到（失败残留僵尸订阅导致查询与轮询行为错误）。
5. **可移植性**：硬编码绝对路径、作者机器专属路径（应从仓库根/`__file__` 推导）；平台差异、编码差异。
6. **行为一致性**：与参照实现/规范的序列化、边界判定是否一致（编码、分隔符、字节计数、精度、深度限制等）。
7. **健壮性**：非法输入、缺失字段、超大输入、超深嵌套是否导致崩溃/挂死/污染输出通道。
8. **安全/权限**：越权访问、权限绕过、fail-open 风险、注入、凭据泄露。
9. **代码质量**：死代码、重复实现、明显可读性问题（避免过度吹毛求疵）。
10. **性能**：明显的复杂度失控、无界增长、无界队列、忙等。

### 实现度轴子代理 prompt 要点

- diff 命令与提交清单。
- PR 声称的目标（描述/标题/commit message 摘录）。
- brief：「报告：(a) 声明要求中缺失或只完成一半的（空壳、占位、TODO、半成品）；(b) diff 中超出声明范围的行为（夹带改动）；(c) 看似实现但实现方式可能有误的；(d) 错误路径是否齐全（成功路径之外：非法参数、越权、超时、内部错误、资源耗尽）；(e) 边界条件是否覆盖（空输入、超上限、极端值、重复调用、并发、关闭/清理路径）；(f) 测试是否真正覆盖这些路径，还是只测 happy path，测试能否独立、可移植地运行；测试/基建类 PR 验证测试真的断言了目标行为、能驱动真实目标、无环境依赖。每条发现引用声称来源的原句。不超过 400 字。」

## 第 3 步：汇报与修复

- 聚合两轴报告：在 `## 一致性轴` 与 `## 实现度轴` 两个标题下并列呈现（verbatim 或轻度清理）。**不合并、不跨轴重排**——两个子代理分开汇报，正是为了防一轴掩盖另一轴（见「为什么拆轴」）。
- 结尾一行小结：各轴发现数 + 各轴内最严重问题（如有）。不选跨轴「唯一最严重」：那正是拆轴要防止的重排。
- 结论照旧给出：可合并 / 需修复后合并 / 需讨论。
- 对「是否应修 / 如何修 / 方案取舍」有分歧时，与用户确认后再动手，不擅自大改。
- 确认修复后：定位修改，遵循项目约定（语言、注释、风格、提交规范）。

## 第 4 步：测试验证

- 运行 PR 相关测试及受影响的既有测试；修复前后对比证明修复有效。
- 涉及路径、环境、构建的修改务必在本地实际跑一遍，不能只看代码。

## 第 5 步：文档同步

- 把 PR 改动 + 你的修复追加到项目 CHANGELOG（按「新增 / 修改 / 修复 / 技术债」组织；技术债单列备忘）。
- 接口/行为变化同步协议文档（含修订记录）、README、协作说明；若贡献指南规定了文档要求，一并遵守。
- 不主动新建文档，只更新既有文档；除非用户明确要求。

## 第 6 步：合并与关闭

- 用户确认后：按仓库提交风格提交修复、合并到目标分支、关闭 PR。
- 合并前用 `git status` / `git log` 确认状态；合并后总结改动。

## 第 7 步：工作区收尾

- 确认修复/文档改动均已按项目规范提交推送，无未提交残留；有残留先与用户确认处理方式，绝不擅自丢弃。
- 切回第 0 步记录的原始分支；若 PR 已合并，建议切回主分支并拉取合并后的最新代码（项目约定 rebase 则用 `pull --rebase`；网络/权限失败时如实报告，不强拉）。
- 本地 PR 分支已合并且不再需要时，询问用户是否删除（`git branch -d`），未经确认不删。
- 清理审查过程中产生的临时文件（如有）。

## 汇报输出模板

```text
## 一致性轴
<一致性轴子代理报告：契约/结构/理念/文档同步/跨实现 + CONTRIBUTING 合规（存在列合规/不合规项 / 缺失注明） + 潜在问题清单（[阻塞]/[应修]/[建议]，每项含位置、原因、建议）>
## 实现度轴
<实现度轴子代理报告：功能完成度评价，附证据（测试覆盖、边界、错误路径）；无 spec 可对照时注明>
## 小结
- 一致性轴 N 项发现，轴内最严重：…；实现度轴 M 项发现，轴内最严重：…
## 结论
- 可合并 / 需修复后合并 / 需讨论
```

## 为什么拆轴

一个改动可以过一轴而挂另一轴：

- 完全符合项目规范与排查清单，但实现错了需求 → **一致性轴过，实现度轴挂**。
- 严格实现了声称的功能，但破坏项目契约与约定 → **实现度轴过，一致性轴挂**。

分开汇报让一轴无法掩盖另一轴。两轴报告并列呈现、不合并重排，轴内最严重问题各自标注；跨轴排序会重新引入「一轴掩盖另一轴」的风险，这正是拆轴要防的事。

## 关键经验（跨项目通用）

- 错误路径与清理路径是问题高发区，优先于正常路径审。
- 「文档没同步」与「接口对不上」往往是同一件事，一起查。
- 贡献原则（CONTRIBUTING）合不合规，与接口一致性同样重要，审查前先确认项目有没有贡献指南。
- 可移植性问题是测试/工具类 PR 的高发问题。
- 判定「是否该修」时考虑项目成熟度与用户目标，避免过度工程。
- 大 PR 先按文件分类扫结构，再深入逻辑；小 PR 直接精读。
